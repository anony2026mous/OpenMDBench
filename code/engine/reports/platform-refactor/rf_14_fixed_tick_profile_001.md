# RF-14 Fixed-Tick Performance Profile 001

## 结论

在不改变固定 `tick_seconds=1`、不引入离散事件推进、也不跳过任何仿真 tick 的前提下，MD-AD-002 中等难度的稳态单 tick **存在达到 10 倍实时推进的性能空间**。当前阻碍不是飞机/舰艇/MMG 动力学本身，而是 `SessionLifecycleV2.step()` 为异常回滚而在每个 tick 创建、校验、哈希一个完整且持续增长的 `WorldCheckpointV2`。

10 倍实时意味着 1 秒仿真时间的一个 tick 需要在 0.100 秒内完成。剔除完整检查点后的稳态计算为 0.055--0.070 秒/tick；保留当前完整检查点时为 0.148--0.291 秒/tick，且随对局推进继续变慢，当前实现无法稳定达到 10 倍。

## 范围与方法

- 场景：`MD-AD-002-MEDIUM`，`seed=73`。
- 执行：正式 V2 会话、`FormalRuleAgentTeamV2`，无实时界面、无渲染、固定 1 秒时间步。
- 方法：完成一个预热 tick 后，分别采集 `policy`、完整 `session.step` 和 `world.checkpoint()` 的墙钟耗时；另使用 `cProfile` 采样 3 个 tick，并测量检查点 JSON 大小。
- 环境：Intel Core i7-10875H（8 核/16 线程）、Python 3.11.15。
- 本次仅做读时性能剖析；未修改产品代码，也没有改变日志、回放或确定性语义。

## 观测数据

### 分阶段实测（秒/tick）

| Tick 区间 | 平均完整 `step` | 平均完整检查点 | 检查点占比 | 非检查点计算 |
| --- | ---: | ---: | ---: | ---: |
| 0--4 | 0.846 | 0.046 | 5.4% | 0.800 |
| 5--9 | 0.148 | 0.093 | 62.8% | 0.055 |
| 10--14 | 0.220 | 0.164 | 74.5% | 0.056 |
| 15--19 | 0.291 | 0.221 | 76.0% | 0.070 |

首组包含约 3.8 秒的原生工作器/JIT 启动开销，不代表稳态。稳态阶段中，完整 `step` 的吞吐从约 6.86 tick/s 降至约 3.45 tick/s；而去除完整检查点后的计算仍保持约 14--18 tick/s。

规则智能体决策约 0.005--0.012 秒/tick，因而不是本轮 10 倍瓶颈。

### 检查点体积与耗时

| 世界 tick | 完整检查点耗时 | 检查点 JSON 大小 |
| ---: | ---: | ---: |
| 5 | 0.071 秒 | 284,964 B |
| 10 | 0.174 秒 | 549,875 B |
| 15 | 0.184 秒 | 811,191 B |
| 20 | 0.245 秒 | 1,071,968 B |

检查点大小和构造耗时随 tick 明显累积增长。这与每个检查点携带完整世界状态、实体视图、原生适配器快照、运动账本和世界 tick 账本相符。

### 调用热点

三 tick 的 `cProfile` 中：

- `SessionLifecycleV2.step()`：0.760 秒累计，约 0.253 秒/tick；
- `WorldStateV2.checkpoint()`：0.404 秒累计，约 0.135 秒/tick；
- `WorldCheckpointV2.create()`：0.226 秒；
- 检查点哈希、规范 JSON、Pydantic 校验、递归 plain 化合计占据主要剩余时间；
- `WorldStateV2.advance_tick()`：0.302 秒累计；
- 原生 V2 动力学步进和 MMG 工作器 RPC 合计约 0.013 秒/tick。

因此不能把当前问题归因于 MMG 模型、导弹/飞机运动或渲染；它们不是主要限制项。

## 推荐优化方案（待确认后实施）

1. 将“每 tick 的故障回滚”与“完整、可持久化、可哈希检查点”分层：前者使用仅在内存保存的轻量事务快照或变更集，覆盖本次 `apply_tick` 可能修改的运行时状态及原生适配器状态。
2. 保持每 tick 的权威收据、事件日志和状态演化不变；完整 `WorldCheckpointV2` 仅用于显式保存、配置化间隔、回放锚点或任务结束等需要跨进程恢复的时机。
3. 如完整检查点仍需频繁生成，再为实体视图、任务事实和不可变状态增加版本号/脏标记缓存，避免每次全量递归编码、哈希与校验。
4. 将原生工作器/JIT 预热作为会话就绪阶段的可选优化，消除首 tick 的约 3.8 秒一次性开销，但不把它与稳态 tick 优化混淆。

优化必须落在通用会话/世界层，不得按 MD-AD 场景、阵营或单一实体类型编写特例。

## 不应采用的做法

- 不删除回滚保障，也不在异常路径中留下半更新世界；
- 不通过增大时间步、跳过 tick、跳过收据/日志来制造“10 倍”；
- 不将仿真加速改成离散事件推进；
- 不把完整状态检查点的耗时简单归咎于可视化并绕过权威路径。

## 实施前的风险与验证要求

轻量回滚快照的覆盖范围必须先审计。`apply_tick` 可能更新实体、任务、通信、武器、原生适配器和账本；遗漏任一可变部分都会导致异常回滚后状态不一致。

实施后至少应验证：

1. 相同场景、种子和动作时间线下，每 tick 的实体状态、任务、计分、事件收据与 RNG 结果保持等价；
2. 在动作管线的多个阶段注入异常，确认轻量快照可精确恢复到 tick 前状态；
3. 任意 tick 的完整检查点--恢复与连续运行结果等价；
4. 并发会话之间无原生状态串扰；
5. 覆盖 1、10、20 以及长局（建议 1,800）tick 的基准，确认中位数稳定低于 0.100 秒/tick，且检查点尺寸、内存和耗时不再无界累积；
6. 固定 tick 的 1 倍与 10 倍运行保持相同的权威状态、日志和回放结果。

## 复现命令类别

- 使用 `.venv/bin/python` 创建 `MD-AD-002-MEDIUM` 正式 V2 会话；
- 完成一次预热后测量 `FormalRuleAgentTeamV2`、`session.step` 及 `world.checkpoint`；
- 对三 tick 使用 `cProfile`，并以 JSON 序列化长度衡量完整检查点体积。

本报告不包含生产代码变更，因此无需新增自动化测试；结论基于上述可复现的性能采样和源码调用链审阅。
