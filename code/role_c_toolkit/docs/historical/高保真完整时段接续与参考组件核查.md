这是包含引擎、记录层和系统调度的墙钟观测，不能据此断言是哪一组件造成逐步变慢；也不能把它当成无仪器引擎性能。它说明不能简单按最初 30 tick 线性推算完整场景耗时。单局既定超时仍为 7200 秒，未为通过门禁临时修改。若后续触发超时，应记录为运行未完成，不能判作任务失败终局或定律被证伪。当前进程继续运行，后续终局/超时以报告和独立审计为准。

只读源码检查进一步发现：`hifi_trace.py::TracedSession.step` 每个 tick 调用 `world_view.checkpoint()` 并对返回的完整对象递归序列化求哈希；源引擎 `openmdbench/world/factory_v2.py::checkpoint`（约 6562 行起）重新构建包含全部 `motion_ledger`、`world_tick_ledger` 等累计历史的 checkpoint。`checkpoint_v2.py` 还包含历史一致性校验。因此当前测量层明确引入了随历史增长的工作量，若每 tick 线性增长，总开销可能呈平方增长；这只是代码路径支持的复杂度风险，尚未分段计时证明其占总耗时的比例。

不能把这一风险直接当成原引擎主循环缺陷，也不能在运行中删除历史字段或减少哈希覆盖后继续宣称同一版本的完整逐 tick 回放验证。若需后续优化，应在独立、明确版本化的记录器中先分段计时并做完整内容等价验证，再另开批次；当前录制器不改动。
