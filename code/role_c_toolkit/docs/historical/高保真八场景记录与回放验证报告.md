## 2. 记录与回放语义

`hifi_trace.py` 在源评测入口外包裹记录层，输出：

- 目标提交：完整命令、原始提交时钟与 broker 接受/拒绝回执。
- 执行输入：执行前全部活动目标，以及己方实体状态（包括固定设施）。
- 执行结果：动作批次及提交回执、目标状态报告、引擎 step 回执。
- 执行后状态：全部实体的位置、速度、生命周期、健康、能源、弹药与组件状态。
- 每步世界检查点哈希、broker 状态哈希和整条 transition 哈希。世界检查点包含世界 RNG 等引擎已有检查点字段。

记录的裁判状态仅用于离线核验，没有新增向规划器提供的观测。

固定回放不重新调用原规划策略：保留原编排器的时钟与执行流程，用无决策的占位规划器替代策略调用，在 broker 提交边界装入已记录的完整命令。这样不会因为反事实中的弹药过滤等上游处理重新改写已固定的目标。若原目标时间线没有后续提交，不临时编造新决策。

本轮只验证同组件、同配置的自身回放，尚未验证更换执行器后的反事实正确性；两者不能混为一谈。

## 3. 核验结果与适用范围

运行报告给出的通过标记之外，`audit_hifi_traces.py` 重新读取全部原始轨迹，检查文件哈希、逐 tick 顺序、t→t+1 状态时钟、命令内容与 transition 指纹，并重新比较原运行/回放的版本、配置、指纹、决策和主要结果字段。16 份报告核验没有发现错误。

另以 IE-01、seed=100、30 tick 做未加记录的原始跑局对照。除以下四个耗时字段外，其余结果字段完全一致：`elapsed_seconds`、`ticks_per_second`、`step_mean_seconds`、`step_max_seconds`。这项被动性检查只覆盖该场景的该时间段，不能外推成全部场景和完整生命周期的无扰动证明。

各运行记录了 390 个选定引擎/评测 Python 文件、场景/Catalog YAML 和项目配置文件的哈希，运行前后无变化；记录脚本在批次内也未修改。这是指定文件集合的版本证据，不声称包含整个机器或仓库所有文件。

新增 18 项测试，包含映射代理与模型序列化、固定命令覆盖边界、禁止编造后续目标、时钟错位、内容篡改和缺失 tick 检测。连同既有测试，**60/60 项通过**。结果核验由本任务中的另一脚本完成，不是外部审稿者的独立认证。

## 4. 为什么暂不输出正式 B_if 数字

每局只有三次规划提交；按全部活动语义目标集合编码，目标组合数为 3–5，最小类别样本量均为 1。己方全状态编码各有 21 个不同值，包含明显重复与时间依赖。

这不满足直接套用普通连续 KSG 的前提，也不满足当前严格混合类型估计器对所有类别支持数的要求。不能删除稀有类别、伪造连续噪声或把估计失败记为零。因此审计输出 `B_if_formal_estimate = null` 并附原因，而不是给出看似可用的数字。

后续必须先固定目标/状态编码、生命周期处理和采样单位，再用完整时段与多 seed 检查支持数、重复值、时间相关和负对照。当前 30-tick 检查只证明数据链路可用，不构成 D3 梯度检验。

## 5. 归因实验仍需补齐的输入

论文 §5.1 要求经过单域任务独立验证的 oracle 规划器和执行器。本轮检查的高保真 eval 入口中尚未找到这两类已验证组件；规则组件的存在不等于 oracle 质量成立。

已向用户询问对应实现路径或参考组件定义。在其明确之前，可以继续做好接口和回放工作，但不能将规则组件替换试验直接标成论文 oracle 归因验收通过。五类故障、三档执行故障剂量、真正的双层故障案例、参考组件质量与完整时段回放检查仍未完成。
