## 耗时定位

| 调用路径 | 调用数 | 累计秒数 |
|---|---:|---:|
| 记录器 `TracedSession.step`（含原引擎 step） | 30 | 48.873 |
| 原引擎 session `step` | 30 | 11.779 |
| world `checkpoint` | 30 | 28.044 |
| checkpoint `create` | 30 | 17.969 |
| checkpoint `compute_checkpoint_hash` | 60 | 16.523 |
| 记录器 `digest`（所有类型指纹合计） | 90 | 8.165 |

这些累计时间存在父子嵌套，**不能逐行相加**。checkpoint 生成明确占用了大量时间；它重建累计历史并进行完整性检查和哈希，而记录器随后又序列化整个 checkpoint 求自身指纹。这使前一轮只读代码分析中的性能风险获得了实际调用证据。

但不能将本表直接当作正常运行的性能比例：cProfile 会改变 Python 调用成本，本次还与主批次并行运行，存在 CPU 调度竞争；没有用它推断未经计时的完整轨迹总耗时，也不据此承诺某项修改的加速倍数。

## 对当前实验的处理

原八场景完整时段批次继续运行，不改动其记录器、超时设置和原运行/回放条件。不能为了提速静默删去 checkpoint 历史、RNG、内部状态或减少验证覆盖后仍声称同一种完整逐 tick 一致性检查。

后续若需要优化，应在独立版本中区分“接口测量数据”与“完整隐藏状态一致性证明”的成本，先验证替代实现覆盖的内容和确定性，再新开批次。当前计时结果既不构成正式测量，也不解决参考 oracle 缺失、混合变量估计条件和三档干预等尚未完成的要求。

## 两次单步墙钟看门狗触发与处理

上述 IE-04 回放实际完成 1199 条 transition，120 次决策，24 个检查点，逐步指纹与原运行**全部一致**，自然终局回执也出现在 tick 1199；但引擎入口在最后一步测得 67.0 秒，超过默认 `--step-timeout 60` 秒，因而将报告标为 `aborted="step_timeout at tick 1198..."`，退出码 1、`exact_match=false`。独立审计只报 `aborted_or_source_changed`，**不能把逐步一致偷换成完整回放验收通过**。其评分卡因此受中止标记影响，也不能与无中止原跑局直接当同条件最终效用比较。

IE-05 单场景原运行同样在 tick 999→1000 的一步测得 60.5 秒而触发 60 秒看门狗；1000 条 transition、100 次决策、20 个检查点均有记录，但未达到终局，不能用于完整时段测量。原批次 `artifacts/hifi-ie05-terminal-stride50-v1/` 的回放按失败跳过并保留进度。两例说明记录器 checkpoint 开销与 Windows 调度竞争足以让**测量进程**触发入口墙钟阈值；它们不是游戏任务失败，也不构成定律反例。
