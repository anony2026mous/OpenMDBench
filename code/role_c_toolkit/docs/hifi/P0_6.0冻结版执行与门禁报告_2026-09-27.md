## 1. 执行边界与证据等级

使用 6.0 正式场景包 IE-04、IE-10、IE-11 作版本清单；运行冒烟以 IE-10 和 IE-11 为主。seed `9901` 专用于开发性 P0 审计与修复复测，**不是**预定的确认性 seed `201–203`。运行被明确截为 1、11、20 或 170 tick：没有任何一局自然终局，所有快照分数均从主成绩表排除。最初 P0 运行时未改动引擎、正式场景或 checkpoint；随后按用户要求，仅对 IE-11 场景中两架诱饵的实体／控制器编号及对应生成源作了定向修复。该修复改变 IE-11 resolved hash，因此形成**修复前、修复后两个不可混用的场景版本**；IE-04、IE-10 resolved hash 未变。哈希比对范围是已列入清单的 27 个代码/场景/目录文件加 3 个权重文件，不代表整个仓库所有文件均被冻结或干净。

**通俗解释：**这些是正式比赛前检查设备、规则和题面的短跑，不是完整比赛。途中显示的分数只是仪表盘快照，不能用于宣称哪种架构更好。

## 3. 六臂接口与历史数据复用检查

IE-10 同 seed `9901` 六臂各运行 1 tick：`rule`（即设计中的 `rule-rule`）、`llm`（`llm-rule`）、`rule-rl`、`llm-rl`、`rl`、`pure-llm` 均启动并生成报告与日志，接口冒烟 6/6 通过。三个 LLM 臂各实际发送 1 次请求，未见请求错误或空响应。**修复前** IE-11 的 `llm`、`llm-rl`、`pure-llm` 各运行 11 tick，各实际请求 2 次，共 6 次请求，均有非空回复，无运行中止；旧提示与响应保存在旧批次的 `*_requests.json`。初次 P0 的 9 局加两局回放均非自然终局，主成绩合格数为 **0/11**。**修复后** IE-11 同三臂、同开发 seed 各重新运行 11 tick，各发出 2 次真实 vLLM 请求，共 6 次；均无中止、请求错误或空回复，[新批次逐局请求与 manifest](artifacts/p0_20260927_d1_fix/)保留原文。修复后这 3 局也仍是**非终局冒烟**，没有被追加到旧版本的主成绩表。本报告不比较跨版本快照分数，也不以这些少量请求推断长期可靠性。

检查 6.0 `_w1_runs` 中与三场景有关的 119 份候选历史 JSON：在当前可取得的文件内，满足“逐局完整来源信息且自然终局”双条件的可直接认证记录为 0，确认性 seed `201–203` 的记录为 0；还存在同一场景/臂/seed 的多 tag 重复格。明细见 [`existing_inventory.json`](artifacts/p0_20260927/existing_inventory.json)。这只否定**本次扫描范围内的直接抵扣**，不否定角色 B 将来提供的其他带原始日志和哈希的合格轨迹。`rule-rl` 权重 `theta_arm5_v12.npz` 为 `goal_source=rule`、训练 iteration 11；`llm-rl` 权重 `theta_arm5_llm_reward_v9.npz` 为 `goal_source=llm`、iteration 3；纯 RL 使用无 Goal 的 `theta_rl_legacy2.npz`。两种 RL 执行权重训练来源/预算不同，四格差值目前只能是已训练部署系统的描述，不是“只换规划器”的因果效应。权重元数据中的训练时源码哈希与当前代码有 0/4/5 项差异（依次为 `rl`/`rule-rl`/`llm-rl`），已在来源清单中保留，不能静默混同。

**通俗解释：**所有选中的“选手”都能上场，但还没有完成一场能计分的比赛。旧记录缺少足够的身份证明，不能随便拿来凑一张公平的六臂成绩表；两名 RL 选手也不是同一训练条件下只换了一个零件。

## 4. IE-11 实际信息流审计：修复前失败、修复后信息门禁通过

6.0 的默认 `llm_briefing=withheld` 未把 `attack.timeline` 的未来事件直接写进三种 LLM 臂的实际请求。修复前后两批各 6 条请求均未含预设未来短语（如 `spawn_tick=`、`real air package`、`decoy screen`），且旧版把真实主攻误写为“非威胁”的文本未出现。初次 P0 **仍因接触编号泄露而失败**；以下保留当时的负向证据，再给出本次修复复测。

修复前 IE-11 的真实实体 ID 是 `intruder.decoy-01/02`。正式 V2 会话在 [`factory_v2.py`](../source-code/openmd/source-code/source_codes/openmdbench/world/factory_v2.py) 第 3895、3930 行按 `sensor.contact.{owner_entity_id}.{target_entity_id}` 生成接触 ID，于是“decoy”真值进入公开 `contact_id`。旧版 170-tick 规则观测追踪中，第 1 tick 已看到带 `decoy` 的公开 ID；97 个不同接触 ID 中有 22 个带此字样；真正主攻空中实体首次见于 tick 150。原始证据见[修复前观测](artifacts/p0_20260927/ie11_contact_trace.json)。

修复前三个 LLM 臂各自第 2 次、约 tick 10 的**实际发送请求**中也都出现 `sensor.contact....intruder.decoy-01/02`；见[修复前逐请求审计](artifacts/p0_20260927/ie11_information_audit.json)。当时的 **NO-GO 是正确历史结论**，不能将这些原始文件改写成已通过。为只堵这个直接泄露入口，现将 IE-11 两架诱饵及其控制器的实体 ID 改为与真实空中目标同格式的 `intruder.uav-05/06`，并同步 `_gen_ie_set_ext.py` 的生成定义；保留 `decoy` 标签、无武器配置、位置、行为、tick 150 主攻出场与评分。未改引擎接触 ID 机制、其他场景或模型权重。

修复后同 seed 的 170-tick 规则观测追踪得到 **97 个公开接触 ID，0 个含 `decoy`**；所抽查的公开接触行也不含该角色词。中性编号 `uav-05` 首次见于 tick 1，真实主攻 `uav-01` 首次见于 tick 150，符合原场景节奏；见[修复后观测原文](artifacts/p0_20260927_d1_fix/ie11_contacts_after.json)。三个 LLM 臂的 6 条真实请求中，修复前各有 1 条包含 `intruder.decoy-*`，修复后均为 **0/2**；修复后第 2 次请求可见中性 `intruder.uav-05/06`，但没有将其标成诱饵，也没有未来时间线或“declared DECOYS”说明。逐臂原始请求分别见 [`llm`](artifacts/p0_20260927_d1_fix/ie_11_decoy_screen_llm_s9901_t11_leakfix_requests.json)、[`llm-rl`](artifacts/p0_20260927_d1_fix/ie_11_decoy_screen_llm-rl_s9901_t11_leakfix_requests.json)、[`pure-llm`](artifacts/p0_20260927_d1_fix/ie_11_decoy_screen_pure-llm_s9901_t11_leakfix_requests.json)。因此，按 P0 预定的“实际公开观测／提示不得直接暴露目标角色真值”标准，**当前修复版 IE-11 的 D1 信息门禁默认通过**。提示中的“可能有诱饵”是非定向的任务提醒，不提供哪个接触是诱饵；固定编号可能被事先掌握场景映射的系统记住，因此后续 D1 能力实验仍需排除预先记忆／训练污染，而不能只凭本门禁宣称自主识骗已获证明。

**通俗解释：**我们没有删除诱饵，只把玩家会看到的“诱饵”名字换成普通空中目标编号。旧版确实泄题；新版的雷达和真实模型输入中不再直接指认哪架是假目标，所以可以开始测试识骗能力。若某个智能体事先背过“05/06 就是假目标”，那仍不算自主识骗，后续实验要防这种情况。

## 5. D1′、D2 与重放/随机源的最低限度审计

修复前 IE-11 的隐藏角色标签曾泄露，因此那批数据不能用于 D1 无标签辨别率或诱饵误打／保弹的因果解释。修复后的**输入信息门禁已通过**，但只有同一开发 seed 的 11-tick 冒烟，没有足够的独立、自然终局样本来计算 D1 辨别率、误打率或最终保弹效应。修复前后 11-tick `llm` 短跑均出现过对真实诱饵的开火；这只说明目标引用／开火链路还能运行，不能证明或否定长期识骗能力。D2 所需的同 seed、同场景、同评分口径的三种纯架构**自然终局**分数仍不存在，因此“最好纯基线”、headroom 和 P/E/I/B 核算均记为**不可计算**，不是 0。资源分配错误率和纯基线成败分布也不能从上述截断局可靠估计；不使用旧 seed 7/11 的单点结果替代。

IE-10 `rule` 臂在 seed `9901` 独立运行两次、各 20 tick，逐字段比对场景、seed、tick 数、终局状态、设施/实体、开火、事件摘要、分层指标、评分表等 16 个报告字段，结果完全一致；见 [`baseline_replay_audit.json`](artifacts/p0_20260927/baseline_replay_audit.json)。这是**相同 seed 的基线重跑**，不是“导出原目标/动作后注入回放”，更不是轨迹分叉后的外生随机事件逐项对齐。P0 没有实施介入条件，故不声称已满足 P2/故障归因所需的自身重放与强反事实门禁。未来若做介入，须先证明目标/动作回放、源哈希、终局和事件匹配；分叉后随机流对不齐时只估计相同 seed 分布下的平均系统效应。

**通俗解释：**现在题面不直接泄密了，但我们还没做足够多场完整比赛，不能宣布识骗能力及格。两次从相同起点重跑，前 20 步确实一样；这像确认录像机能重复播放开头，不等于证明换一个动作后所有随机事件也会逐件相同。

## 6. 门禁结论、停止规则与下一步

| P0 检查 | 结果 | 后续含义 |
|---|---|---|
| 端点/模型、列管哈希、评分单测 | 通过（限定上述范围） | 可继续对这些固定对象做接口审计 |
| IE-10 六臂、IE-11 三种 LLM 臂接口 | 冒烟通过；全部非终局 | 不能计入 P1/P2 主表 |
| IE-11 未来时间线及旧“主攻非威胁”错误 | 修复前后实际提示均未见 | 与接触 ID 修复分别审计 |
| IE-11 隐藏诱饵真值信息门禁 | **修复前失败；当前修复版通过（默认采用）** | 可以启动 D1 能力实验；不得把门禁通过写成识骗能力已证实 |
| 历史局直接抵扣、D2/headroom | 尚无可认证终局格 | 不计算胜负或公式 |
| 同 seed 基线重跑 | 20-tick 报告匹配 | 介入后强回放仍未验证 |

下一步统一使用**修复后 IE-11 resolved hash**，重新生成逐局 manifest；修复前 IE-11 报告和 seed 只作历史审计，不抵扣修复后主表。修复版已完成三条 LLM 路径的实际提示审计、规则观测追踪和短跑目标引用／开火冒烟；后续每个确认性 seed 仍应保存原始提示并复核无标签输入，尤其要排除固定 ID 映射被智能体事先记忆或进入训练资料的可能。按预定 seed `201–203` 启动 P1 完整局后，才能计算无标签辨别、误打／保弹、最好纯基线和效用差；P2 Goal 裁剪与 P3 可靠性也仍是后续工作。如果未来换模型、改提示、重生成场景或泄露再次出现，应重新打开信息门禁，而非沿用本次通过结论。

**通俗解释：**这次已经修好了最直接的泄题入口，允许进入下一轮完整比赛。旧分数不能拿来凑新题的成绩；如果将来换题、换提示或有人把编号答案教给智能体，还得重新检查是否泄题。
