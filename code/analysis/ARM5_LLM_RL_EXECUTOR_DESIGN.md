# 第五臂设计：LLM 规划层 + RL 执行层（消融）

> 目的：把混合臂里**基于规则的离散执行器**（`GOAIExecutorV2`）换成
> **RL 训练出、直接输出速度/航向/开火具体值**的执行层，其余一切不变，
> 以隔离"执行器"这一个变量。
> **原有 rule / 混合 LLM / 纯 LLM / 纯 RL 四臂全部保留不动**，这是新增的第五臂。

---

## 1. 先定接口契约（不可含糊）

读 `v2_agent.AgentV2.__call__` 得到的既有调用链：

```
observation = session.world_view.observation(observer_faction_id=faction)   # 按阵营过滤
_refresh_unit_roles()          # _unit_roles: id->frozenset(tags)；_meta: id->活实体
observation.own_entities 只保留可机动单元
if tick == 0 or (tick - last_plan_tick) >= plan_interval:
    goals = planner.plan(observation, tick, broker.poll_reports(), _unit_roles, meta=_meta)
    goals = [g.to_granularity(...)]           # 可选粒度降级
    goals = 丢弃弹药耗尽单元的 intercept/ambush/reserve 目标
    broker.submit_goals(goals, step=tick)
exec_stats = executor.act(session, tick)      # ← 只替换这一层
```

所以 RL 执行层必须实现**同一个签名**：

```python
def act(self, session, tick) -> {"submitted": int, "fires": [record, ...]}
```

**唯一被替换的东西就是 `act()` 内部**：规则版把它变成
"目标类型 → 几何解算 → 离散动作"；RL 版把它变成
"目标编码进观测 → 一个网络 → 直接输出每单元 (绝对航向, 绝对速度, 开火目标)"。

LLM、规划节奏 `plan_interval`、broker 的目标词汇、观测过滤、弹药耗尽过滤
**全部不动** —— 否则测不出执行器的差异。

### 目标词汇（必须编码，来自 `goai_protocol.GOAL_TYPES`）

11 型：`waypoint / patrol / track / intercept / hold / return / loiter /
barrier / ambush / reserve / disengage`。

`GoalCommand.parameters` 常用键：`unit_id`、`position`、`target_id`、`speed_mps`、
`duration`，以及分型专用：`axis_deg`/`radius_m`/`arc_deg`（barrier）、
`standoff_m`（ambush）、`commit_within_m`（reserve）。

`constraints`（`{type, value}` 列表）、`priority`、`deadline` 也都在命令里。

## 2. 网络与算法选型（我定的，附理由）

### 选型结论

| 项 | 选择 | 理由 |
|---|---|---|
| 算法 | **PPO**（与纯 RL 臂同一套） | 直接复用已加固的 `ie_rl_train.py`（numpy↔torch 逐位一致门禁、采样 logprob ≡ 训练器重算门禁、小 minibatch 损失门禁、截断守卫、LPT 负载均衡、奖励逐项分解）。换算法等于把这一整套验证要重做一遍，收益不明。 |
| 网络 | **一个共享主干 MLP（obs⊕goal → 256 → 256），per-slot 头** | 与纯 RL 臂结构一致，便于对照；参数量 ≈73 万，与现有数据预算（数万条转移）匹配。 |
| 目标编码 | **按单元的 goal 特征块**（unit block 10 → 10+G） | 每个 goal 都带 `unit_id`，把该目标编码进**它所属单元的槽位**天然对齐动作头；未分配目标的单元用一个 "none" one-hot。避免了"全局 goal 向量 + 需要网络自己学会把 goal 匹配到单元"这一层隐式学习负担。 |
| 与规则执行器的关系 | 同签名、同信息集、**同速度约定**（见 §3 的开关） | 消融要求只变执行器。 |

### 明确否决的方案

* **行为克隆规则执行器做热启动**：那会让消融变成"规则执行器 + RL 微调"，
  混淆了被测量的变量。要从零学。
* **注意力 / per-entity 编码器**：当前数据预算（数万条转移）会过拟合；
  留到编成扩到 30–50 单元时再上（届时顺带解决 GPU 利用率）。
* **换 SAC/TD3 等 off-policy**：样本效率的收益被"重做整套验证"的成本抵消；
  且本项目已证实真正的坑在数据标定与协议，不在算法。

### 目标特征块设计（G 维，每个单元）

```
goal_type one-hot (12)          # 11 型 + "none"
has_target (1) + target slot index one-hot 或 (sin,cos,dist) 到目标 (3)
position 相对本单元 (dx, dy) 归一 (2)   # waypoint/patrol/loiter/return/barrier/reserve 用
speed_mps / 本单元上限 (1)
priority (1) + deadline 剩余 (1)
分型标量: radius_m / standoff_m / commit_within_m / arc_deg 归一 (2，按型取用)
```
合计 **G ≈ 22**。unit block 10 → 32，观测 2866 → 2866 + 16×22 = **3218**。

## 3. 审计第 1 轮：输入对等 + 速度标定（**发现重大既存缺陷**）

### 3.1 发现：**规则执行器自己的速度表就是错的**（与 §7 的平台分类缺陷同类）

`v2_executor.ExecutorConfigV2.speed_by_tag`：

```python
speed_by_tag = {"uav": 40.0, "usv": 8.0, "interceptor": 40.0, "picket": 8.0}
```

实测对照（IE-01，从目录读的真实 `max_speed_mps`）：

| 单元 | 标签 | 执行器用 | 目录真实上限 | 倍差 |
|---|---|---|---|---|
| `defender.uav-01..04` | `('defence','combat-unit','interceptor')` | **40.0** | **80.0** | **2×** |
| `defender.usv-01..02` | `('defence','combat-unit','usv','surface')` | **8.0** | **10.0** | 1.25× |

注意它**恰好**靠 `interceptor` 这个兜底键避开了我在 RL 侧踩的 `uav` 标签坑 ——
但代价是**全体空中单元只用了物理上限的一半**，水面用 80%。
**这意味着已记录的三臂基线（rule / 混合 / 纯 LLM）都是在"空中单元半速"下测出来的。**

### 3.2 连带结论：现有四臂对照在速度包线上**从未同等**

* 修复前：纯 RL 臂被压在 **10 m/s**（平台分类错误），而三臂是 40/8 → 纯 RL 吃亏。
* 修复后：纯 RL 臂用 **80/10**（目录真实），而三臂是 40/8 → 纯 RL 占优。

**两个方向都不公平。** 这是我在给出四臂读数时没有说明的前提，必须更正并解决。

### 3.3 解决方案：把速度约定做成**一个显式开关**，两种都跑

在 `ie_rl_env` 与执行器之间引入**单一事实来源**，取值二选一：

| `speed_source` | 语义 | 用途 |
|---|---|---|
| `legacy_tags` | 沿用执行器现有表（空 40 / 水 8） | 与**已记录**的混合臂头对头，只隔离执行器 |
| `catalog` | 读 `dynamics.max_speed_mps`（空 80 / 水 10） | 物理正确；需要**重跑三臂基线** |

第五臂**两种都跑**：`legacy_tags` 给出可比的消融结论，
`catalog` 量化"陈旧速度表"值多少分。这样歧义是被**测量**出来的，而不是被藏起来。

**待办**：纯 RL 臂也要在明确约定的 `speed_source` 下重训，使五臂同口径。

### 3.4 输入对等表（规则执行器消费什么，RL 执行层就要拿到什么）

| 规则执行器 `GOAIExecutorV2` 的输入 | RL 执行层对应物 | 状态 |
|---|---|---|
| broker 活动目标（`goal_type`/`unit_id`/`position`/`target_id`/`speed_mps`/`constraints`/`priority`/`deadline`） | §2 的 per-unit goal 特征块 | 待实现 |
| `_unit_roles`（标签）与 `_meta`（活实体：弹药、健康、绑定） | 单元块已有：域、健康、弹药比、包线、速度上限 | 已有 |
| 自持接触（`contact_required`） | `own_contact[(unit,target)]` + 掩码 | 已有 |
| 每 (entity, weapon) 冷却账本 `_last_fired` | **缺**：环境目前只用引擎返回的 executed 计数 | 待补（否则 RL 会反复提交被冷却拒绝的动作） |
| 目标认领去重 `_engaged_targets` / `_shots_on_target` / `overkill_cap=2` | **缺**：RL 可能多机同打一个目标 | 待评估，见审计第 3 轮 |
| `retreat_when_out_of_ammo` | 掩码已让无弹药单元不能开火；脱离行为靠策略学 | 待评估 |
| `objective_m`（屏障/预备的距离基准） | 全局块 + goal 的 position | 已有 |
| `arrive_radius_m` / `track_standoff_m` 等战术常量 | 作为 goal 特征里的标量或直接给策略 | 待定 |

**结论（第 1 轮）**：速度标定必须先解决成开关，目标编码必须按单元对齐，
冷却账本缺失需要补 —— 这三项不解决就开始训练，等于把执行器差异和标定差异混在一起。

## 5. 审计第 2 轮：逐项排查硬编码物理量

速度已经在**三处**各自出错（RL 平台分类 10 vs 80、规则执行器表 40 vs 80、
`SPEED_BY_CLASS` 43 vs 80），所以这一轮把物理量逐个与目录对照，判据是
**凡目录里有的，代码里不得有常量**。

| 物理量 | 目录真值（拦截无人机） | 代码里的值 | 判定 |
|---|---|---|---|
| `max_speed_mps` | **80.0** | 已改为从目录读；`SPEED_BY_CLASS` 仅作兜底（已标为近似值） | **已修** |
| `MAX_SPEED_MPS = 43.0` | — | **完全未被引用（死常量）** | **已删** |
| `max_turn_rate_deg_s` | 30.0 | RL 层不直接使用（引擎内解算） | 无需读 |
| `max_vertical_speed_mps` | 20.0 | 同上 | 无需读 |
| `max_acceleration_mps2` | 8.0 | 同上 | 无需读 |
| `min_altitude_m` | 0.0 | 未使用 | 见下 |
| `POS_SCALE_M` | 地图范围约 `-20000..40000` m | 常量 40000 | 可接受（仅归一化，不构成正确性） |
| `AIR_ALTITUDE_THRESHOLD_M` | — | 常量 50.0 | **已验证安全**（见下） |

### 高度：两层都不控制 ⇒ 不构成消融混淆，但都是能力缺口

查 `v2_executor.py:365`：规则执行器的导航命令是
`"altitude_m": position[2]` —— 即**保持当前高度**。RL 层同样保持高度
（`submit_action` 里 `"altitude_m": float(pos[2])`）。**两层一致 ⇒ 没有不对称**，
消融不会被这一点污染。

代价是**两边都不能变高/变深**，因此都无法用高度规避或进入武器高度窗口。
这是五臂共同的能力缺口，记录为已知限制（要支持需同时改两层的动作语义）。

### `AIR_ALTITUDE_THRESHOLD_M = 50.0` 已实测验证

按可观测高度把接触判为"空中/水面"，实测飞行高度（IE-04）：

| 目标 | 高度 z |
|---|---|
| 我方拦截无人机 | **800 m** |
| 来袭无人机 | **150 / 250 / 300 / 150 m** |
| 水面单元与固定设施 | **0 m** |

50 m 的门槛对两边都有 ≥3 倍余量，判定正确。且该阈值与规则臂
`interception_graph.air_altitude_threshold_m` **同口径**，四臂一致。

### 本轮结论

速度类常量已全部收敛到"目录读 + 显式兜底"，死常量已删；高度两层一致；
阈值已用实测高度验证。**没有发现新的正确性缺陷。**

## 6. 审计第 3 轮：单元↔目标分配、冷却账本、去重与超杀

### 6.1 冷却：**当前不构成约束（已用目录数值证明），但仍补进掩码**

从目录逐武器读出（两个 bundle 一致）：

| 武器 | `cooldown_ticks` | `rounds_per_action` |
|---|---|---|
| `weapon.interceptor-missile` | 5 | 1 |
| `weapon.loitering-munition` | 5 | 1 |
| `weapon.air-interceptor-munition` | 5 | 1 |
| `weapon.surface-missile` | 3 | 1 |
| `weapon.suicide-warhead` | 0 | 1 |

决策周期是 5 tick，最大冷却也是 5 tick ⇒ **一个单元在一次决策内最多只能开一枪**，
冷却根本卡不住。所以"RL 侧没有 `_last_fired` 账本"这件事**当前无害**。

**但仍然补上**，因为"今天数值恰好对得上"正是速度表和 500–8000 m 包线变成 bug 的方式 ——
三个都是"曾经正确、然后被复制而不是被读取"的值。改动：

* `_weapon_profile_full()` 一并返回 `cooldown_ticks`（从目录读）；
* `Slot.cooldown_ticks`；
* 环境记录每单元**已执行**射击的 tick（`_last_fire_tick`），
  从回执的 executed 子项里按**最长匹配**还原实体 id
  （实体 id 含点，`rl.fire.defender.uav-01.123` 不能直接切分）；
* `fire_mask` 在冷却未过时关闭该单元的开火列。

门禁 `_w1_test_fire_cooldown.py` **7/7**，且**故意构造出厂场景里不存在的长冷却**
（`cooldown = 0/1/5/30`，经过 0 tick）：0 时开火列开放，1/5/30 时全部关闭 ——
**忽略冷却的实现会在这条上失败**，所以它不是空断言。

### 6.2 去重与超杀：**故意留给策略学，并作为消融的一部分记录**

规则执行器有 `deconflict_fire=True`（跨 tick 认领）、`_shots_on_target`、
`overkill_cap=2`（同一目标最多投 2 发）。RL 侧**没有**这些。
这是**有意保留的差异**：消融要测的就是"手写去重 vs 学出来的去重"。
代价会体现在记分卡的 `ammo` 层（纯 RL 臂 0.655，发/杀 3.6–4.3 而 rule ≈2.0）。

**结论**：不补去重，但要在最终对照里把它作为解释项列出来，
并新增一个**弹药集中度**诊断（每个目标被投入多少发）用于归因。

### 6.3 单元↔目标分配：**编码为输入，不强制遵守，并测量遵守度**

契约：LLM 通过 `GoalCommand.parameters["unit_id"]` 指定执行单元。
规则执行器读取该字段并据此解算。RL 执行层把该目标编码进**它所属单元的槽位**，
但**不硬约束**网络必须执行它。

理由：规则执行器本身也不是刚性执行（它有 `reserve` 自动前出、`patrol` 扫掠等
自主行为），硬约束 RL 网络会人为削弱它，测出来的差异就不再是"执行器"。
因此改为**测量目标遵守度**（被中性化的目标中有多少是当期指派的目标），
作为消融的附加指标，而不是把它变成约束。

### 6.4 本轮结论

冷却已从"未读"变为"读自目录 + 掩码生效 + 有能失败的门禁"；
去重是**有意保留**的消融变量并配了归因诊断；
分配语义确定为"输入条件 + 测遵守度"，不硬约束。

## 7. 审计第 4 轮：协议与"目标条件化"特有的奖励漏洞

### 7.1 本消融的**中心有效性威胁**：策略可以完全无视 LLM 的目标

训练奖励里**没有任何一项引用 goal**（它只奖励击杀、纵深、设施、终局、弹药）。
于是存在一个退化路径：RL 执行层学会完全忽略 LLM 的指派，
去最大化记分卡 —— 那它就会**收敛成纯 RL 臂**，
第五臂的读数等于第四臂，"LLM 层"变成装饰。

**这不是靠加奖励项解决的**：给"遵守目标"加奖励会把执行器绑死在 LLM 的计划上，
连坏计划也照做，反而测不出执行器的价值。
**处置：测量而不是约束。**

新增指标 **目标遵守度（goal adherence）**：
在每个中性化/开火事件上，检查被打击的目标是否等于该单元当期指派目标的
`parameters["target_id"]`；输出"遵守比例"与"纯自主比例"。

判读方式（写死，避免事后解释）：

| 观察 | 结论 |
|---|---|
| 遵守度高、分数与 rule 执行器相当 | RL 执行层**忠实执行**了 LLM 计划 |
| 遵守度低、分数显著高于纯 RL 臂 | 学习到的自主性带来了增量 |
| 遵守度低、分数 ≈ 纯 RL 臂 | **LLM 层在此架构下无贡献**（这是一个有价值的负面结论，必须如实报告，不得包装） |

### 7.2 从既有四臂继承的协议约束（已踩过坑，此处不重复踩）

| 项 | 规则 | 证据 |
|---|---|---|
| 采样模式 | **必须随机采样**评测 | 同一权重同种子同场景：确定性 0.1342 vs 随机 0.6613（5 倍假差） |
| 种子 | 训练 1000–1004，评测 7/11/13/17/19，**不相交** | 在评测种子上训练会让 RL 见过那次抽签，三臂不训练，不公平 |
| 截断代理 | 已修为"设施存活 − 已推进到位的袭击份额" | 旧代理对门口袭击给 +2.0 |
| 有效性校验 | `ticks_run>0` **且**有终局结论 **且** 未中止 | 曾有 tick 0 中止局被记分卡给出 0.3889 并静默进矩阵 |
| 速度约定 | 五臂必须同 `speed_source` | 见 §3；空域单元两组约定差 **2 倍** |

### 7.3 控制节奏不对称（**已知的、未被隔离的因素**）

| 执行器 | 提交节奏 | 命令有效期 |
|---|---|---|
| 规则执行器 | **每 tick** | `valid_until_tick = tick + 1` |
| RL 执行层（本设计） | 每 5 tick | `tick + 5` |

规则执行器每 tick 重新解算，控制带宽是 RL 执行层的 5 倍。
**这是执行器性质的差异，不是学习能力的差异**，必须在结论里声明。

两点缓解与判读：

* 纯 LLM 臂的 `--plan-interval` 是 **10**，所以 5 tick 的执行节奏**比纯 LLM 臂更细**，
  RL 执行层不是对照里最粗的控制器；
* 若首轮结果含糊，用 `--decision-interval 1` 做一次带宽对齐的追加评测
  （只增加评测成本，不需重训：动作是绝对量，重发同一指令语义一致）。
  **不默认这么做**，因为每 tick 重新采样会让指令在 tick 粒度抖动，
  只有确定性模式才干净。

### 7.4 本轮结论

目标遵守度**必须测量并写死判读标准**；协议约束沿用四臂已验证的五条；
控制节奏差异**记录为未隔离因素**并给出对齐方案。

## 8. 审计第 5 轮：LLM-RL 集成

规则执行器之上的编排在 `AgentV2.__call__`，第五臂**完全复用**，逐项确认：

| 机制 | 现状 | 对第五臂的影响 |
|---|---|---|
| 固定节奏重规划 | `tick==0 or (tick - last_plan_tick) >= plan_interval` | 不变 |
| 目标粒度降级 | `g.to_granularity(goal_granularity)` | 不变（goal 编码必须能吃降级后的形态） |
| 弹药耗尽过滤 | 丢弃 dry 单元的 `intercept/ambush/reserve` | 不变；RL 掩码另有"无弹药不能开火" |
| broker 抢占/优先级 | `submit_goals` + `PRIORITY_EPSILON` | 不变；RL 执行层要读**当前生效**的目标，而非刚提交的 |
| 目标过期/陈旧复用 | 规则版有 `stale_plan_reuse` 计数 | 第五臂同样统计，作为健康指标 |
| LLM 失败回退 | `fallback_count` / `parse_failures`（混合臂 seed 7 实测 13 次 parse 失败、0 次回退） | 不变；第五臂沿用同一计数 |
| 可行性 | broker 回 `infeasible` 的目标 | RL 执行层收到"不可行"目标时仍需给出动作（无目标 → 走 "none" 编码） |

**关键实现要求**：RL 执行层必须从 **broker 的当前活动目标**读取条件，
而不是从"上一次 LLM 返回的列表"读取 —— 否则目标被抢占后执行层仍按旧目标行动，
这与规则执行器的语义不一致（规则版每 tick 从 broker 取）。

**本轮结论**：集成面全部复用既有编排，无新增机制；
唯一实现要求是"读 broker 当前活动目标"。

### 12.1 **新发现：已记录的混合臂基线不能直接用作对照**

同一个混合臂（`--planner llm`）、同一场景 IE-01、**同一种子 7**、同一配置，重复跑 5 次：

| 运行 | 分数 | tick |
|---|---|---|
| 记录的 `s1` | 0.8377 | 45 |
| `regress_hybrid`（本次重构后） | 0.8995 | 68 |
| `rep2` / `rep3` / `rep4` | **0.9047 ×3（逐位相同）** | 54 |
| **统计** | **mean 0.8903, sd 0.0295, range 0.0670** | |

两条结论：

1. **混合臂不是逐位可复现的**，同配置重复跑有 **sd≈0.03、极差 0.067** 的波动；
   而 `rep2/3/4` 三次逐位相同，说明波动更可能来自**代码/提示词版本差异**

2. 因此 **`s1` 那份记录的混合臂基线（0.8377）与当前代码的运行（0.8995/0.9047）
   不可比** —— 它是在更早的代码版本下产生的。

并且因为 sd≈0.03，比较阈值不能小于这个量级；若第五臂与规则执行器的差异
落在 0.03 以内，必须多种子重复才能判读。

### 14.0 训练侧的两处加固（第 24 轮）

**① 手工拼 `argparse.Namespace` 是脆的 —— 改为从真 parser 派生**

训练 worker 要给 `run_episode._build_defender` 一个 `args`，我原来**手写字面量**列出


`build_parser()`，worker 用 `build_parser().parse_args([])` 拿**完整**命名空间再覆盖需要的项。
复测：`--help` 正常、命名空间 30 个字段、关键项齐全。

**② 目标来源必须可监控：`--goal-source llm` 会静默回退**

`LLMPlannerV2` 带 `RulePlannerV2` 回退。端点挂掉时它会**静默改用规则目标**，
训练照常继续、奖励看不出异常，但**目标分布已经变了**——这正是"看起来什么都没发生"那类坑。
已在每轮记录 `goal_source_health = {plan_calls, parse_failures, fallback_count,
mean_goal_units_per_decision}`。

### 14.0b 训练用哪种目标：**改用 `llm`，不用 `rule`**

原计划先用 `rule` 目标（免费）验证管线、再用 `llm` 做忠实版。**改为直接用 `llm`**，
理由是方法学的：消融要测"LLM 规划 + RL 执行"，若**训练用规则目标、评测用 LLM 目标**，
一旦第五臂表现不佳就**无法区分"执行器不行"还是"目标分布不匹配"**——
而那正是被测变量本身，等于把混淆项塞了进去。

成本：`rule` 约 190 s/轮（7 场景 14 局）；`llm` 时每 worker 每轮多约 45 次调用
（0.3–0.7 s/次）⇒ 约 **+25%**。用这个代价换掉一个混淆项是划算的。

### 14.0c 更正：`--goal-source llm` 实测约 **4 倍**成本，不是 +25%

我先估"每轮多约 45 次调用 × 0.5 s ⇒ +25%"。**实测错了约 4 倍。**

证据（7 场景 14 局，`--goal-source llm`）：约 17 分钟后只有 5/8 个 rollout 落盘，
而每个 worker 的**累计 CPU 只有约 130 s** —— 即 worker **绝大部分时间在等 LLM**，
不是在算仿真。真实调用耗时是 **3–4 s/次**（提示词含拦截图，很大），不是 0.5 s。
每轮约 930 次调用（6 个全长局 90–100 次 + 8 个截断局 45 次），摊到 8 个 worker
约 116 次/worker ⇒ 350–460 s 纯等待。

**处置（符合"先验证方法、不烧算力"）**：

* **方法验证阶段用 `--goal-source rule`**（约 250–300 s/轮），
  并**显式记录混淆项**：训练目标是规则规划器产的、评测目标是 LLM 产的；
* 该混淆**可以量化**：评测时记录的 `adherence` 正是"执行器跟不跟 LLM 目标"的直接度量。
  若规则目标训练的检查点在 LLM 目标下的 adherence 与规则目标下相当，
  说明目标分布差异不构成实质影响；否则必须做 `llm` 目标的忠实版训练；
* 忠实版（`--goal-source llm`）留到方法确认无误后再跑。

### 14.0d 顺带修掉一个 10 倍的性能陷阱（行为保持不变）

`plan_once` 原来**先建完整观测、再检查是否该规划**：每个 tick 都付一次
`ObservationV2` 快照（接触/传感器/己方实体）的代价，而十次里九次直接丢掉。
第五臂训练用 `pre_tick_hook` **每 tick** 调它，于是这个既存的低效被放大成整轮的 10 倍慢。
把节奏检查提到最前面即可，**行为完全不变**——观测只在规划分支里被读取。
复测：rule 臂仍**逐位相同**（IE-01 0.8877 / IE-02 0.8989）。

**② 开火纪律缺失，且代价可见。**
规则执行器有 `assess` 教义 + `deconflict_fire` + `overkill_cap=2`；RL 执行层**一个都没有**
（§6.2 判定为"有意保留的消融变量"）。实测后果：**169 tick 内开了 60 发**
（混合臂在 899 tick 内只开 12–13 发），`ammo` 层掉到 0.333。
这不是"学习 vs 手写"的差异，而是**手写教义被整体拿掉**的差异。

**③ 训练预算不对称。** 规则执行器是人工调过的实现；RL 执行层只训了 20 轮。
把"20 轮学习"与"人工调优"直接比，比的是预算而不是方法。

### 14.6.2 结论与处置（**不把 0.2489 当作方法结论**）

**当前第五臂还不能与混合臂做结论性对比。** 要让它成为公平对照，按性价比：

1. **补开火纪律**（最便宜、收益最明确）：把 `overkill_cap` 这类教义以**掩码**形式加到
   执行层（"同一目标已投入 ≥N 发就不再提供该选项"）。这是把教义对齐，
   使对照隔离"控制策略"而不是"教义有无"。**待做。**
2. **控制节奏对齐实验**：用 `--decision-interval 1` 跑同一 checkpoint，
   量化"每 tick 重解 vs 5 tick 持有"单独贡献多少分差（工具已就绪）。
   **待做。**
3. **用 LLM 目标重训**（消除 train/eval 落差），成本约 4×（实测），
   放在 1、2 确认之后。

在上述三项做完之前，任何"学习型执行器不如规则执行器"的结论都是**过早的**。

### 14.8 **找到并修掉第五臂的真正主因**：同一发离散动作被每个 tick 重复提交

`_execute_goal` 由 `act()` **每 tick** 逐单元调用，而它每次都把缓存里的开火动作**重新提交**；
一个决策窗 5 tick ⇒ 同一发离散动作被提交 **5 次**。两个后果，都实测到了：

* **射击记账被放大 5 倍**，且引擎只接受第一发（其余按冷却/重复拒绝）——
  这正是早先"161 submitted vs 10 executed"的来源；
* **会直接中止回合**：`session.contact_invalid: opaque contact is not a current
  observation owned by the firing entity`（实测 t99）——缓存里的接触在几 tick 后已失效。

引擎文档本就规定离散动作**至多执行一次**，所以"每窗一次"也是正确语义。

**三档对照（IE-01 seed 7，同一 checkpoint，随机采样）**：

| 运行 | 改动 | 分数 | 结局 | submitted fires | ammo | depth | facilities | terminal |
|---|---|---|---|---|---|---|---|---|
| `v5` | 旧代码（无教义、重复提交） | 0.2489 | intruder @169 | 12 | 0.333 | 0.287 | 0.0 | 0.0 |
| `v5_di1` | 教义 + 间隔1（**仍**重复提交） | 0.2885 | intruder @169 | 4 | 1.0 | 0.298 | 0.0 | 0.0 |
| `v5_doc2` | 教义 + **每窗一次** | **0.9011** | **defender @75** | 8 | 1.0 | 0.555 | **1.0** | **1.0** |

**决定性的是"每窗一次"**（0.2885 → 0.9011，且设施全保、守住）。
先前把 `v5_di1` 与 `v5` 的差别归因于"节奏"是**错的**——`v5_di1` 同时改了教义与节奏两个变量，
而且当时重复提交的 bug 还在。**已更正。**

### 14.8.1 但这一分**不能**当作"修好了"——两个必须说清的保留

**① 这是单次随机抽样。** IE-01 上随机读数的种子带宽很宽（纯 RL 臂实测 0.64–0.90），
0.9011 完全可能是好签。**必须多种子才能下结论。**

**② 更要紧：这次胜利的 `on_assigned_ratio = 0.0`** —— 8 发**没有一发**打在 LLM 指名的目标上
（虽然 `with_goal_ratio = 1.0`，即开火的单元都持有目标）。
也就是说**这一分不是靠"执行 LLM 的计划"拿到的，而是靠策略自己的自主性**。

这正是 §7.1 预先写死的"中心有效性威胁"现身：奖励里没有 goal 项，
所以策略可以在**无视指派**的情况下得分。按判读表，这属于"遵守度低"一档，
必须与纯 RL 臂的相对分数一起读才能定性 —— 而那需要 `rl_legacy`（正在训练）。

**因此现在的正确表述是**：方法管线已跑通、重复提交这个真 bug 已修、
第五臂能产出有效且有竞争力的读数；但**"LLM 层是否真的有贡献"这个问题仍未回答**，
且首个信号（在获胜回合里 completely 无视指派）是**偏负面**的。

### 14.10 两个"引擎会拒绝、我方仍然提交"的缺陷 —— 修掉后第五臂稳定在 **0.903**

`session.contact_invalid: opaque contact is not a current observation owned by the
firing entity` **会中止整个回合**（不是只拒绝那一发）。我先后命中两条路径：

**① 缺置信度门槛（已修）**
规则执行器有 `min_conf = min(0.30, contact_confidence)`，其注释直接点出病因：
*"本地门槛不应高于引擎门槛 … 避免'本地合格、引擎拒绝'的错配"*。
RL 掩码只查自持 / 包线 / 目标域，**从不查置信度**。
修法：`MIN_CONTACT_CONFIDENCE = 0.30` 进掩码（并同步进"在包线内"特征，
维持"特征与掩码不得分歧"不变式）。实测 `own_contact` 里的置信度可低到 **0.124**。

**② 接触在动作生效时已从 store 消失（已修）**
读引擎源码得到确切机制：`lifecycle_v2._engagement_request` 调
`contact_store.resolve_owned_observation(evidence_id, owner, current_tick)`，
返回 None 即抛错中止；而 `install()` 规定**每个 evidence_id 只允许一条记录**，
store 又在 `step()` 内重建 —— 于是"决策时发布过的接触，动作生效时可能已经不在了"
（传感器 `update_ticks` 节奏，或目标离开量程）。

修法：**提交前先问引擎自己的解析器**
（`session._world.contact_store.resolve_owned_observation`）；它说不行的就不发。
这不是绕过规则，而是把"中止回合"变成"保持不开火"——引擎既然不会接受这一发，
这个选择本来就不存在。内省失败时 **fail-open** 并计数（"守卫读不到就全部禁射"
比它要防的问题更糟）。

**验证（种子 7 / 11，两者此前都会中止）**：

| | 修前 | 修后 |
|---|---|---|
| seed 7 | abort @t53 | **0.9012** defender @t83 |
| seed 11 | abort @t48 | **0.9011** defender @t75 |

`doctrine` 计数器证明守卫在真做事：`suppressed_unresolvable` = **4 / 1**、
`suppressed_overkill` = 44 / 64、`suppressed_assess` = 7 / 2。
且 `on_assigned_ratio` 从 0.0–0.125 **升到 0.5**（被剔掉的正是那批打不中的）。

### 14.13 对照列的一个真缺陷：纯 RL 臂一直在**训练值 2 倍**的动作保持时长下评测

**证据（读代码，不是猜）**：
* `ie_rl_env` 每个动作覆盖 `decision_interval` tick（`valid_until_tick = tick +
  decision_interval`），训练用的是默认 **5**（`ie_rl_train.py --decision-interval 5`）；
* `run_episode.py` 的 `--planner rl` 分支读的却是
  `decision_interval=int(getattr(args, "plan_interval", 5) or 5)` ——
  `--plan-interval` 是 **LLM 规划节奏**（默认 **10**），而纯 RL 臂根本没有 LLM；
* `_w1_ie_sweep.py` 只对 `llm/pure-llm/llm-rl` 传 `--plan-interval`，对 `rl` 不传，
  于是纯 RL 臂拿到默认 10。

**后果**：`rl_main5sto`、`rl_legacy` 这些存档读数的动作保持时长是训练值的两倍，
是典型的 train/eval 错配；而这一列正是消融要用来判读第五臂的对照列。

**改动**：`run_episode.py` 的 `rl` 分支改读 `--decision-interval`（默认 5 = 训练值），
`_w1_ie_sweep.py` 对 `rl` 也显式传该旋钮。**因此历史纯 RL 读数全部作废**，
正在用 `theta_rl_legacy2.npz` + 保持 5 重跑 8 场景 × 5 种子（tag `rlb2`）。

**顺带发现并处理的一个坑**：这个改动落在 `hold5/hold10` 批次运行中间，会让
同一个 tag 里混进两种代码版本（改动前起的局实际是保持 10）。这类"代码切换点两侧
混批"会让两组读数都不可解释，所以那批数据**整批删除重跑**，不留"看起来能用"的中间态。

### 14.14 新增**诊断臂 `rule-rl`**：规则规划 + RL 执行层（无 LLM）

**为什么必须加**：主消融 `llm` vs `llm-rl` 同时含两个与执行器无关的噪声源 ——

1. **LLM 非确定性**：同配置、同种子重复 5 次实测 mean 0.8903 / **sd 0.0295** /
   其中 3 次逐位相同；
2. **规划器本身的质量差**：`rule` 臂在 IE-01 上 5 个种子是
   `0.8877 / 0.6064 / 0.1528 / 0.1435 / 0.2727`（**sd 0.325**），而所有 LLM 臂
   稳定在 0.903 ± 0.002。IE-01 的分差主要来自**规划层**，不是执行层。

`rule-rl` 用**确定性规则规划器**驱动**同一个 RL 执行层**，于是
`rule` vs `rule-rl` 只隔离"执行器换成学习型"这一个变量，且**不含任何 LLM 成本**，
可以 5 种子 × 8 场景跑满。

**关键性质（决定了它的判读地位）**：第五臂的 checkpoint 是用
`--goal-source rule` 训练的（见 §14.0b），而 `rule-rl` 在评测时提供的正是
**规则规划器目标** —— 所以 `rule-rl` 是**训练/评测目标分布一致**的那次评测，
而 `llm-rl` 带有已知的目标分布偏移。两者都要报：前者证明"执行器学到了什么"，
后者回答"换成 LLM 规划上层之后还成立吗"。

实现只动一处：`run_episode.py` 的 `executor_factory` 条件从
`("llm-rl")` 扩到 `("llm-rl", "rule-rl")`，`planner` 仍走 `RulePlannerV2`
（`--plan-interval 10`，与 `rule` 臂和训练时的目标源完全一致）。

冒烟（IE-01 seed 7）：**0.9047 defender_success**，8 发全中、设施 1.0、终局 1.0，
`with_goal_ratio=1.0`、`on_assigned_ratio=0.125`，
`doctrine={assess 5, overkill 17, unresolvable 2}` —— 守卫与教义都在工作。

### 14.16 第 6 轮审计：**射击掩码 vs 引擎交战门禁，逐条对照**

前 5 轮都是"我怀疑哪里不对就去查"，这一轮改成**从引擎源码反推合法集**，再逐条对表。
结论是：**引擎有两类不同的拒绝**，混起来就会写错掩码 ——

| 类别 | 位置 | 表现 |
|---|---|---|
| **会话级校验** | `lifecycle_v2._engagement_request` | 抛异常 ⇒ **整个回合中止** |
| **交战级合法性** | `combat/system_v2.py` 的 `checks` 字典 | **静默拒绝**，不耗弹、不推进 RNG |

会话级只查两件事：`weapon_ref` 能解析出**恰好一条**弹药绑定（否则
`session.payload_invalid`），以及接触能被
`contact_store.resolve_owned_observation` 解析（否则 `session.contact_invalid`）。
交战级才查 `contact`（`quality>0`、`owner==attacker`、目标一致、
**`age_ticks <= max_contact_age_ticks`**、**`confidence >= minimum_contact_confidence`**）、
`envelope`、`ammunition`、`cooldown`、`target_domain`、`attacker_lifecycle`、
`capability`、`relationship`、`components`、`energy`、`model_trust` 等 14 项。

**关键事实：这两个阈值来自传感器目录，而不是场景的 defence 段。**
IE 全集目录里每个传感器的声明都是

```
stale_after_ticks: 12   engagement_max_age_ticks: 12   minimum_contact_confidence: 0.0
```

而**代理可见的接触字段只有**
`contact_id / observer_entity_id / estimated_position_m / observed_tick / age_ticks /
confidence / quality` —— **看不到传感器声明的阈值**。所以任何本地门槛只能取自
场景声明值，这就是规则执行器那句注释的由来
（*"本地门槛不应高于引擎门槛 … 避免'本地合格、引擎拒绝'的错配"*）。

**逐条对照表**

| # | 规则执行器的门禁（`v2_executor.py:857`） | RL 掩码 | 判定 |
|---|---|---|---|
| 1 | 自持接触存在 | `own_contact[(unit,target)]` | ✅ 一致 |
| 2 | **`age <= contact_max_age_ticks`** | 无 | ⚠️ 见下 |
| 3 | 武器目标域允许 | `_domain_pairing_allowed` | ✅ 一致 |
| 4 | `conf >= min(0.30, config.contact_confidence)` | 常量 **0.30** | ✅ **实测一致** |
| 5 | 包线按**本单位自己的估计**量距 | 同 | ✅ 一致 |
| 6 | 冷却（目录读） | 同 | ✅ 一致 |
| 7 | 弹药 > 0 | 同 | ✅ 一致 |
| 8 | `deconflict_fire` 认领去重 | 无（只有超杀上限） | ⚠️ 见下 |
| 9 | `overkill_cap` | 执行器侧已镜像 | ✅ |
| 10 | `assess` 评估窗 | 执行器侧已镜像 | ✅ |
| 11 | — | `_contact_is_resolvable`（问引擎解析器） | RL 侧独有，见 §14.10 |

**第 4 条我一度怀疑是"我自己引进的不公平"**（因为场景里写的是
`contact_confidence: 0.0`，`min(0.30, 0.0)=0.0` 看起来该是 0），于是去查了取值链路：

* `run_episode._build_defender` 构造 `ExecutorConfigV2` 时**没有传** `contact_confidence`
  ⇒ 用 dataclass 默认值 **0.55** ⇒ `min(0.30, 0.55) = 0.30`；
* 场景里的 `contact_confidence: 0.0` 进的是**规则规划器**的图（`RulePlannerConfigV2`），
  不是执行器。

所以 **0.30 与规则执行器逐位一致，不是不公平**。这条**负面结论也要记下来** ——
否则下次有人看到"引擎阈值是 0.0"就会把掩码改成 0.0，那时才真的变成不公平
（RL 臂能打规则臂不敢打的接触）。

**保留的三处不对称（不修，写清理由）**

* **年龄门（第 2 条）**：规则执行器用 8 tick（顺带发现
  `ExecutorConfigV2` **根本没有** `contact_max_age_ticks` 字段，
  所以 `run_episode` 传的 8 到不了执行器，走的是
  `getattr(..., 8)` 兜底 —— 两者恰好都等于 8，暂无影响）；引擎允许 12。
  实测机制：接触在最后一次探测后**保留 12 tick**（`retained` 按 `stale_after_ticks` 过滤），
  所以规则臂的 8 tick 教义正是它避开"过期接触"的原因，而 RL 执行器靠
  §14.10 的解析器守卫兜住。
  **不把 8 tick 写进 RL 执行器**：把规则的教义一条条搬进"学习型"执行器，
  等于让被消融的对象慢慢变回规则；且它缺失时没有出现病态行为（不像
  `overkill`/`assess` 缺失时 169 tick 打 60 发）。作为**已声明的不对称**保留。
* **去重（第 8 条）**：规则是"同时只许一个单元认领目标"，RL 是"每目标最多 2 发"。
  作用重叠，但语义不同 —— 已声明。
* **解析器守卫（第 11 条）**：RL 侧独有，但它只剔除**引擎必定拒绝**的选择，
  是防"回合中止"的保险，不是额外能力。

### 14.17 消融配对矩阵：**每一对到底隔离了哪一个变量**

用户的要求是"确保消融结构对比合理公平"，所以这一节把**六种方法**的每一对配对写清楚，
而不是只声明"口徑一致"。

| 代号 | 规划层 | 执行层 |
|---|---|---|
| `rule` | `RulePlannerV2` | `GOAIExecutorV2`（规则） |
| `llm` | `LLMPlannerV2`（千问） | `GOAIExecutorV2`（规则） = **混合臂** |
| `pure-llm` | 无（LLM 直接出低层命令） | `PureLLMAgentV2` |
| `rl` | 无 | 一个网络直接出航向/速度/开火 |
| **`llm-rl`** | `LLMPlannerV2`（同一个） | **`RLExecutorV2`** = **第五臂（主消融）** |
| `rule-rl` | `RulePlannerV2`（同一个） | **`RLExecutorV2`** = **诊断臂** |

| 配对 | 隔离的变量 | 判读 |
|---|---|---|
| `rule` → `llm` | 规划层：规则 → LLM | 上层有效性的主证据 |
| **`llm` → `llm-rl`** | 执行层：规则 → 学习型（**上层不变**） | **主消融**；带 A5 目标分布偏移 |
| **`rule` → `rule-rl`** | 执行层：规则 → 学习型（**上层不变、且与训练同分布**） | **诊断消融**；无 LLM 噪声，可 5 种子 × 8 场景跑满 |
| `rule-rl` → `llm-rl` | 规划层：规则 → LLM（执行层不变） | 第五臂自身是否受益于 LLM 上层 |
| `rl` → `llm-rl` | 整体：无规划 + 学习控制 → LLM 规划 + 学习控制 | LLM 层对学习型控制器是否仍有贡献 |
| `llm` → `pure-llm` | LLM 的用法：规划 vs 直接出命令 | 论文 System A/B 对照 |

**六种方法共同固定的东西**：场景集与版本、eval 种子集 {7,11,13,17,19}、
记分卡（同一份 `strategy_metrics`）、引擎树（同一 `refactor` 版本）、
观测权限（同一 `legs/faction` 过滤口径）、`--max-ticks`、报告节奏。

**已知不对称（全部显式声明，不藏）**

| # | 不对称 | 方向 | 处置 |
|---|---|---|---|
| A1 | **控制带宽**：规则执行器每 tick 重解（validity 1），RL 执行器保持 5 tick | 规则侧带宽 5× | `--decision-interval 1` 可量化；对无 LLM 的 `rule-rl` 可以跑 |
| A2 | **采样**：RL 臂随机采样，规则/LLM 臂确定 | RL 侧带方差 | RL 必须按分布期望评（确定性评测曾造成 5 倍假差）；5 种子 |

| A5 | **目标分布**：第五臂 checkpoint 用**规则目标**训练，`llm-rl` 评测用 **LLM 目标** | 第五臂在主消融里 OOD | 这正是加 `rule-rl` 的原因；主消融必须带此声明 |

### 14.18 速度约定必须有 provenance —— 否则整批读数作废

**缺陷**：`ie_rl_train.py --speed-source` 的默认是 `catalog`（平台真实上限 80/10），
而 `rl_agent.py` 读取的默认**也是** `catalog`；但 `theta_rl_legacy2.npz` 是
**显式用 `--speed-source legacy_tags` 训练**的（40/8）。于是当评测命令行没有钉住约定时：

* 训练：速度动作 ×40（空中）
* 评测：速度动作 ×80（空中）

同一份权重的速度指令被放大 2 倍。**实测证据**：`rlb2` 批次报告里
`planner.speed_source = "catalog"`（训练值是 `legacy_tags`）⇒ **整批删除重跑**。

**为什么这个坑特别危险**：不报错、不中止、分数看起来正常 —— 只是"这一臂恰好比较差"，
而它正是消融要用来说明问题的对照列。

**修法（三层）**：
1. 训练时把 `speed_source / goal_features / obs_dim / decision_interval` **写进
   checkpoint 的 meta**，让"这份权重是怎么训出来的"跟着权重走；
2. 评测时优先级 = 显式参数 → checkpoint meta → 环境变量 → **报出 provenance**
   （`speed_source_provenance` 进记分报告，`_w1_arm_table.py` 会把"推断来的"标出来）；
3. `_w1_ie_sweep.py` 增加 `--rl-speed-source`，对照批次一律显式传值。

**同源问题（顺带记下，未改）**：`pure-llm` 在 `run_episode` 里被硬编码成
`speed_max_by_tag={"uav":45,"usv":10,...}` —— 这是**第三张**速度表。
它不在执行器消融的配对里，但会让"五臂总表"里的纯 LLM 臂与其他臂的速度口径不同，
所以在总表里读纯 LLM 的绝对分数时必须带这条声明。

### 14.19 速度约定**确实会改变结论**，而且暴露出一个更根本的几何事实

`rule-rl`（规则规划 + RL 执行层，无 LLM）在两种约定下各跑 3 个种子：

| 场景 | 种子 | `legacy_tags`（空 40 / 水 8） | `catalog`（空 80 / 水 10） | 差 |
|---|---|---|---|---|
| IE-01 | 7 | 0.9047（59 tick） | 0.9005（100 tick） | −0.004 |
| IE-01 | 11 | **0.6634（899 tick）** | **0.9053（58 tick）** | **+0.242** |
| IE-01 | 13 | 0.9043（71 tick） | 0.9025（86 tick） | −0.002 |
| IE-02 | 7 | 0.9035（124） | 0.9042（122） | +0.001 |
| IE-02 | 11 | **0.8323（899）** | **0.9088（119）** | **+0.077** |
| IE-02 | 13 | 0.9010（122） | 0.8996（161） | −0.001 |

**4/6 对在 ±0.004 内**（那些种子本来就被守住），但 **种子 11 差 0.24 / 0.08**。

**原因不是"训练/评测分布不符"，而是几何**：`legacy_tags` 给拦截无人机的上限是
**40 m/s**，而 IE 集的来袭者巡航 **43 m/s**（`attack.speed_mps: 43.0`）——
**防御方比来袭者慢**。于是能否拦住取决于初始几何（种子决定的出生位置），
有些种子**在物理上就追不上**，只能靠迎头几何赌一把。`catalog`（80 m/s）则总能追上。

这同时解释了规则臂 IE-01 为什么 sd 高达 0.325（5 局 3 局失守）——
**它用的是同一张 40/8 表，受同一个几何限制**。

**对消融的三点结论**：

1. **对照必须留在 `legacy_tags`**：只有这个约定下两臂的速度表相同，
   否则比的是"谁跑得快"而不是"谁控制得好"。规则执行器的表是硬编码的，
   不给它开 `catalog`，所以 RL 侧也不能开。
2. **由此产生的共模方差必须用配对统计消掉**：所有臂共用同一个引擎种子，
   同一 (场景, 种子) 上的两臂是**配对观测**（同一条抽签流）。
   独立比均值会把"这个种子几何上就打不着"算进两臂各自的 sd，
   把 0.24 的真差淹没在 ±0.3 的 sd 里。`_w1_arm_table.py` 因此新增
   **配对差**一节：逐种子相减，判据 `|mean| > 2·sd 且 > 0.03`。
3. **`theta_arm5_rule.npz` 的训练约定无法从存档断言**。最接近的证据是训练侧
   goal 探针记录 `_w1_runs/rl/_probe_goal.jsonl`：
   `{"speed_source": "legacy_tags", "goal_features": true}`，而该字段由
   `ie_rl_train.py` 从 `args.speed_source` 填入（第 648 行）——
   所以**那一族**第五臂训练确实带 `--speed-source legacy_tags`；
   但存档只覆盖 `arm5_smoke`（09-22 20:40），主训练 `arm5_rule`（23:05）
   的启动命令没留档。因此 meta 里 `speed_source` 保持 **None**，
   只在 `speed_source_hint` 里记下这条推断，**不写进断言字段** ——
   写进去会让"猜的"警告消失，而那正是要保留的信息。

### 14.20 第 7 轮审计：**学习型执行层不上报目标状态 ⇒ 两个 LLM 臂的规划器看到的东西不一样**

**发现**：`act()` 里那一半簿记（激活 pending 目标、可行性筛查、`failed`/`infeasible` 上报）
是**共用**的（`v2_executor.py:507-527`），但**还有一半在 `_execute_goal` 里**：
规则执行器会在目标达成/丢失/超时时 `self._post(...)`，而 `RLExecutorV2` 覆盖了
`_execute_goal`，于是**一次都不上报**。后果不是"少了个日志"—— LLM 规划器
**消费** `StatusReport`，所以两个臂喂给（同一个）规划器的进度图景不同：

| 臂 | `goals_completed` | `goals_accepted` | 场景/种子 |
|---|---|---|---|
| `llm`（混合） | **3** | 35 | IE-01/7 |
| `llm-rl`（第五臂，修前） | **0** | 50 | IE-01/7 |
| `llm`（混合） | **5** | 60 | IE-02/7 |
| `llm-rl`（修前） | **0** | 61 | IE-02/7 |
| `rule-rl`（修前） | **0** | 33 | IE-01/7 |

**修法**（`RLExecutorV2._report_goal_state`，只补**簿记**、不碰**控制**）：
逐条对齐规则执行器实际会上报的终止情形 ——

1. **deadline 超时** → `timeout`（同一判断式）；
2. **`intercept`/`ambush`/`track` 的目标从接触表消失** → `completed(target_lost)`
   （`contacts` 由共用的 `_contacts_by_id` 生成、按 **contact_id** 键，
   与规划器写进 `target_id` 的形式一致，所以判据与规则执行器**同一条**，不是形似）；
3. **`waypoint`/`return` 到达 `arrive_radius_m`** → `completed`
   （并**刻意不**镜像 `patrol`/`loiter`：规则执行器在那两类上不报完成，而是转扇面扫掠）。
   瞄点取自基类自己的 `_goal_position()`，**不复制几何** ——
   速度表、火控包线、目标编码器各自出现两份互相矛盾的实现，都是"复制一份算术"造成的。

**刻意不镜像的一条**：规则执行器在上报终止后会**把单元停下**；RL 执行层**保留策略的
航向/速度命令**。哪一边更好正是消融要问的问题，所以只对齐信息、不对齐控制。

**修复后实测**（同一 LLM 规划器、同种子）：

| 场景 | 臂 | `goals_completed` | `goals_accepted` | 分数 |
|---|---|---|---|---|
| IE-01 | `llm`（混合） | 3 | 35 | 0.9047 |
| IE-01 | `llm-rl` | **2**（修前 0） | 42 | 0.9036 |
| IE-02 | `llm`（混合） | 5 | 60 | 0.9096 |
| IE-02 | `llm-rl` | **2**（修前 0） | 66 | 0.9036 |

规划器的进度图景从"完全收不到"变成"同量级"。剩下的 `goals_accepted` 差
（42 vs 35、66 vs 60）来自上面那条**刻意保留**的控制差异（不停机 ⇒ 规划器会继续派活），
已作为 A8 声明。

**顺带说明**：不能用 `llm` 的 3 去比 `rule-rl` 的 0 下结论 —— 那两个臂的**规划器不同**
（LLM vs 规则），目标类型分布本来就不同。要比较上报是否对齐，必须是**同一个规划器**
下的 `llm` vs `llm-rl`。

### 14.22 控制带宽（A1）量化尝试：**这个实验不能只改节奏**，并给出为什么不改规则臂

`rule-rl`（同 checkpoint、同种子、无 LLM，只改 `--decision-interval`）：

| 场景 | 种子 | di=5（训练值） | di=1（每 tick 重解） |
|---|---|---|---|
| IE-01 | 7 | 0.9047 | **0.2885（失守）** |
| IE-01 | 11 | 0.6634 | **0.9086** |
| IE-02 | 7 | 0.9035 | 0.9001 |
| IE-02 | 11 | 0.8323 | 0.6791 |

**方向不一致，而且不能当成"带宽效应"来读**：`--decision-interval 1` 同时改了两件事 ——
节奏 5→1，以及**采样次数 ×5**。RL 执行层每次决策都是**重新采样**一个动作，
所以 di=1 相当于把动作噪声注入率也乘以 5（IE-01 seed 7 直接掉到失守就是它的后果）。
要单独量化带宽，必须"保持 5 tick 的动作、但每 tick 重解"，这只能从**规则侧**做
（把规则执行器的重解节奏放粗到 5），而那要动一个**被保留的基线臂**。

**为什么不改规则侧**：

1. A1 的方向是**对学习型臂不利**（规则侧带宽 5×）。也就是说它是**保守偏置**：
   如果在这个偏置下学习型执行层仍然不落后，结论只会更稳；如果落后，则存在歧义 ——
   而这一点已经作为已知限制写在 §14.17 的 A1 里，不会被当成"方法结论"。
2. 改规则执行器（`valid_until_tick` 从 1 变 N、并按 N 跳过重解）会**同时**改变
   目标激活延迟、开火机会与状态上报节奏 —— 那不是"只改带宽"，
   而是又造出一个"两个变量一起动"的对照组，正是 §14.8 更正过一次的错误。
3. 回归基准（规则臂逐位不变 `0.8877/0.8989`）是当前唯一能证明"没碰坏基线"的门禁，
   为一个保守偏置去动它，风险收益不成比例。

**若将来要做干净版本**，正确设计是：给 `ExecutorConfigV2` 加 `hold_ticks=1`（默认 1 ⇒
现有读数不变），`_navigation` 的 `valid_until_tick` 用 `tick + hold_ticks`，
`act()` 在非边界 tick 直接返回"不重解、不开火"，然后跑
`rule --hold-ticks 5` vs `rule-rl --decision-interval 5`，此时两个变量只剩执行器。

### 14.23 **最重要的发现：这一臂以前根本不看计划** —— 归因、两次失败的修法、两个真根因

#### 14.23.1 现象：目标块对输出几乎没有因果影响

写了归因工具 `_w1_policy_input_attribution.py`：在**真实回合**（规划器真的在出目标）里取状态，
然后**逐块**做两件事 —— 置零该块、按该块自身标准差加噪 —— 测量**解出的航向角**变化（度）。
对 `theta_arm5_v2`（已训 20 轮）：

| 输入块 | 宽度 | 置零后航向变化 | 说明 |
|---|---|---|---|
| global | 6 | 1.3° / 1.5° | |
| unit（自身状态） | 160 | **30.2° / 14.4°** | 最大 |
| contact（目标槽） | 140 | 2.1° / 2.7° | |
| **pair（单元×目标，含提前交点方位）** | 2560 | **14.2° / 29.9°** | 第二大 |
| **goal24（计划块）** | 384 | **7.2° / 8.0°** | **明显偏小** |

策略**自己的动作噪声 σ = 0.224 rad = 12.8°**。也就是说：把整块计划抹掉，
航向只动 7-8°，**不到策略自身噪声的 0.6 倍** —— 网络收到了计划，却几乎当作没有它一样在飞。

#### 14.23.2 第一版结论**过强**，以及它为什么被推翻（方法论记录）

第一版探针测"把计划里的目标方位旋转 ±90°，航向跟着转多少"，得到**斜率 0.001**，
我据此写了"计划块是装饰品"。但同一探针作用在 **pair 块的提前交点方位**上也是 0.002 ——
**连策略本该用来制导的特征都测不出响应**，说明是探针的问题，不是结论。补两个对照才看清：

* **单个特征旋转测不出影响**：pair 块 2560 维、goal24 384 维，任何**单个**维度在 MLP
  第一层都没有杠杆 —— 这是稀释，不是"没被使用"；
* 正确的仪器是**整块置零**（上表）；
* **灵敏度标定**（对非目标块加 σ=0.02/0.1/0.3/1.0 噪声）给出 0.4°/1.6°/4.9°/**21.6°**：
  网络会响应，只是**整体增益很低**。

**正确表述**：计划块有可测但**很弱**的影响（7-8°），弱于策略自身噪声（12.8°），
而 pair 块有两到四倍杠杆。"装饰品"这一说法**已更正**。

#### 14.23.3 两个真根因

**根因 A：奖励从头到尾不关心"打谁"。** 任务奖励只看结果（击杀 1.0、设施 −4.0、
终局 ±2.0、深度 0.5、弹药 −0.005/发）—— **把哪一架打下来完全等价**，于是梯度里
没有任何一项要求网络去读"我被指派了谁"。这不是编码器的问题：实测**每个活单元都拿到了目标**
（`has_target` = 1.000），信息一直在，只是没理由用。

**根因 B：计划的信息表述太薄。** 同一个方位，pair 块用 320 行重复表达
（16 单元 × 20 目标），计划块只用**每单元 2 个数**（sin/cos）塞在 384 维里。

#### 14.23.4 修法与**两次失败**（每次先短程验证，不直接烧 3 小时）

| 尝试 | 改动 | 短程验证结果 | 判定 |
|---|---|---|---|
| gs1 | 势能奖励 w=0.25 | goal24 **7.2°→5.6° / 8.0°→4.9°**（**下降**） | ❌ 权重太小 |
| gs2 | w=2.0（8×） | goal24 **5.5° / 6.4°**，r_goal 仅 0.14–0.47 | ❌ 仍不动 |
| gs3 | 暖启动 + 指派掩码 | `assign` 块 **blockstd=0.000**：掩码几乎全空 | ❌ **我自己的 bug** |
| gs4 | 修好掩码来源 | goal24 **10.6°（IE-01，↑）** / 3.4°（IE-05）；r_goal **0.44–0.76 / 1.5–2.0** | ⏳ 方向正确，正式训练中 |

**势能奖励**用 Ng/Harada/Russell 的 potential-based 形式：
`Φ(s) = −mean(单元到自己被指派目标的自有估计距离)/POS_SCALE`，
`r_shape = w·(Φ(s′)−Φ(s))`，w=2.0、命中被指派目标 +0.15/发、整段上限 2.5。
势能式的性质是**不改变最优策略**，所以不会教出"盲从"；它做的是让**指派本身**进入回报，
逼网络去读它（w=0.25 时 r_goal 只占回报 1-2%，等于没有压力）。

**指派掩码**（`_assignment_block`，新增 320 维）：用**策略已经会 attend 的布局**重述同一件事
—— 每个 (单元, 目标) 一个"这是指派给我的吗"旗标。信息量没变，变的是**读取成本**。

**我自己的 bug（gs3）**：`_assigned_targets()` 当时只在该单元**自己的接触表**里解析
`target_id`，而规划器经常给的是**别的观察者**的接触 ID（同一架来袭者）。实测后果：
掩码在 IE-01/IE-05 上分别只有 **1 个**旗标点亮（应为 4 和 9），新块基本是**空的** ——
"加了掩码却没用"这个结论本来是假的。改为按**阵营级**接触表解析后 `mask_sum = 4 / 9`，与指派数一致。

**暖启动**（`_w1_warmstart_theta.py`）：观测 3250 → 3570，旧 `trunk0.w` 按输入轴**零填充扩充**，
其余数组逐位复制；新块初始为 0 ⇒ **行为与旧 checkpoint 等价**
（`_w1_test_warmstart_equivalence.py`：heading/speed/fire/value 最大差 1e-7，PASS）。
这样"加了掩码后行为变了"只能归因于新块被学出来，而不是初始化噪声。

#### 14.23.5 判据（以后任何人改这一臂都按它验收）

* `_w1_policy_input_attribution.py`：**计划块置零效应 ≥ σ（12.8°）**，
  否则这仍是一个"收到但不读计划"的策略；
* `goal_source_health.mean_assignment_flags_per_decision` 与 `mean_r_goal` 必须非零
  —— 掩码全空或 r_goal=0 时，"执行计划"这件事根本没被测量；
* `_w1_test_goal_shaping.py` 11/11（纯 RL 臂奖励**逐位不变**、换指派必须改变 Φ、上限生效）。

### 14.25 LLM 目标训练的成本实测（**决定不把它当第一步**）

`--goal-source llm` 实测：6 worker、12 局/轮，**55 分钟没跑完第 1 轮**
（端点本身健康：小请求 0.2 s；真实规划调用 ~8-10 s，6 个并发客户端互相排队）。
按此外推 12 轮 ≈ **6-8 小时**，而当时的瓶颈（网络不读计划）**训练再多也不会改变**。
所以顺序改为：先用**规则目标**（~6.5 分钟/轮）把"会不会用计划"做出来并验收，
再决定是否用 LLM 目标微调；评测侧仍用 LLM 目标（调用量小得多，可以承受）。
