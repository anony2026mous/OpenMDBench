# LLM-RL 消融实验设计（对比公平性规范）

> 目的：在**跑完整基线之前**把"实验方法本身"固定下来，使六条臂的对比在结构上公平、
> 可复现、可判读。任何一条读数只有同时满足本文件的口径才允许写进结论。
> 配套：`LLMRL_CURRENT_AUDIT.md`（纠错与实测）、`_w1_paired_table.py`（配对表生成器）。

## 1. 六条臂 —— 一个 2×2 因子设计 + 两条"单侧"臂

决策链是两级：**规划层**（产出目标 / goals）× **执行层**（把目标变成每个平台的速度与航向）。

### 1.1 命名规范（以此为准，其它文档一律照此）

**`llm-rule` = LLM 规划层 + 规则执行器**，就是代码里的 `--planner llm`，
也就是最初那套混合方法（此前在文档里被叫作"冻结 llm"——**这个叫法已废止**）。
它的规划器 / LLM 客户端 / 规则执行器**仍然一律不许改动**，但这条是**约束**，
不再拿来当臂的名字。

| 名字 | 规划层 | 执行层 | 代码 | 角色 |
|---|---|---|---|---|
| `rule-rule` | 规则规划器 | 规则执行器 | `--planner rule` | **基线格** |
| `llm-rule` | LLM 规划器 | 规则执行器 | `--planner llm` | 规划层主效应（执行器固定为规则） |
| `rule-rl` | 规则规划器 | **RL 执行层** | `--planner rule-rl` | 执行层主效应（规划器固定为规则） |
| **`llm-rl`** | LLM 规划器 | **RL 执行层** | `--planner llm-rl` | 本项目目标臂 |
| `rl` | 无（RL 直接输出动作） | 无 | `--planner rl` | 纯 RL 单架构基线 |
| `pure-llm` | LLM 直接输出动作 | 无 | `--planner pure-llm` | 纯 LLM 单架构基线 |

简写规则：`<规划层>-<执行层>`。代码里的 `--planner rule` 在读表时写作 `rule-rule`。

> 历史叫法对照：`llm-rule` 过去被写作"冻结 llm / 冻结臂"（**废止**）；
> `rule-rule` = `rule`；`rl` = 纯 RL；`pure-llm` = 纯 LLM。
> 代码 flag、checkpoint tag、文件名一律不改，只有文档里的**臂名**统一成上面的写法。

### 1.2 要主张的结论 —— ★ 混合架构是**两条**基线，两条都要赢

**用户更正（2026-09-24）**：本文档早先把 `llm-rule` 当成"必须被打败的对照"，**理解错误**。
"混合架构"指的是下面**两条**基线，**两条都必须优于其它方法**：

| 混合基线 | 规划层 | 执行层 | 代码 |
|---|---|---|---|
| **混合 A = `llm-rule`** | LLM 作为规划层 | 规则执行器 | `--planner llm` |
| **混合 B = `llm-rl`** | LLM 规划层 | RL 执行层 | `--planner llm-rl` |

"其它方法" = 三条单架构基线：`rule-rule`（纯规则）、`rl`（纯 RL）、`pure-llm`（纯 LLM）。

因此判据是 **6 个不等式**，每条混合臂各 3 条：

1. `llm-rule` > `rule-rule`、`llm-rule` > `rl`、`llm-rule` > `pure-llm`
2. `llm-rl` > `rule-rule`、`llm-rl` > `rl`、`llm-rl` > `pure-llm`

**`llm-rl` vs `llm-rule` 不是胜负关系**（两者同属混合家族，谁高都是好消息）；
它们各自只要压住三条单架构基线即可。`rule-rl`（规则规划＋RL 执行）是**诊断臂**，
用来量"执行层单独换掉值多少分"，不参与上面的判据。

要分解出机制，还需要两条主效应（各自独立成立）：

* **执行层主效应**：`rule-rl` − `rule-rule`（规划器固定为规则，只换执行层）
* **规划层主效应**：`llm-rule` − `rule-rule`（执行器固定为规则）；
  `llm-rl` − `rule-rl`（执行层固定为 RL）

交互项 = `(llm-rl − llm-rule) − (rule-rl − rule-rule)`：衡量"两级都用学习件"是否比"只换一级"更值。

## 2. ★ 约定一致性（本文件最重要的一条）

**一个 RL checkpoint 只能匹配一种目标来源。** 训练时 `--goal-source rule|llm` 决定
RL 执行层观测里"目标块"和奖励里"被指派目标"的来源；部署时 `llm-rl` 喂的是 LLM 目标、
`rule-rl` 喂的是规则目标。**用错来源 = 部署分布与训练分布不一致**，与之前的
"速度约定错配"（`catalog` vs `legacy_tags`）是同一类缺陷。

checkpoint 的 `_meta.goal_source` 是判据（`ie_rl_policy.read_meta`）：

| checkpoint | iteration | `goal_source` | 语义版本 | 正确归属 |
|---|---|---|---|---|
| `theta_arm5_llm_reward_v9` | 3 | **llm** | `shared_rl_executor_reward_v9` | `llm-rl` |
| `theta_arm5_llm_full_ie03_v10` | 1 | **llm** | `shared_rl_executor_reward_v9` | `llm-rl` |
| `theta_arm5_v11` | 7 | rule | `shared_rl_executor_reward_v9` | `rule-rl` |
| `theta_arm5_v12` | 11 | rule | `shared_rl_executor_reward_v9` | `rule-rl` |
| `theta_arm5_v2` … `v4` | 4–15 | rule | 旧语义 | 仅历史 |
| `theta_rl_legacy2` | — | — | 无目标块（obs 2866） | `rl`（纯 RL） |

**纪律**：`llm-rl` 只能用 `goal_source == "llm"` 的 checkpoint；`rule-rl` 只能用
`goal_source == "rule"` 的；两者的**训练配方必须逐项相同**（迭代数、场景集、超参），
否则比较的是训练预算而不是目标来源。当前 v9/v10 只训到 iter 3 / 1，
而 v11/v12 训到 iter 7 / 11 ⇒ **这两对之间还不是等预算对照，报告里必须写明**。

**待办**：把 `llm-rl` 侧（`--goal-source llm`）续训到与 `rule-rl` 侧同量级，
才能让"规划层主效应"在等预算下成立。训练含 LLM 调用，约 40 min/iter。

## 3. 运行口径（每一条 run 都必须满足）

| 项 | 取值 | 理由 |
|---|---|---|
| 场景数据 | 不改（15 m/s 面面弹是**有意设计**） | 设计裁定；要适配的是教义，不是数据 |
| `llm-rule` 臂 | `llm` 的规划器 / LLM 客户端 / 规则执行器一律不动 | 实验设计硬边界 |
| LLM | 关思考；`max_tokens=1024`；`plan_interval=10` | 与 `llm-rule` 同构 |
| RL 决策间隔 | `--decision-interval 5` = 训练值 | 历史上这里的错配（读 `plan-interval`）已修 |
| 速度约定 | `--rl-speed-source legacy_tags` | 必须等于 checkpoint 训练值 |
| 采样 | `--rl-stochastic`（按分布采样，不取逐头 argmax） | argmax 会把整个单元群压成同一选择 |
| 超杀释放 | **关**（默认） | 与规则执行器同语义；开启只用于诊断 |
| 种子 | 报数用 7/11/13/17/19；训练用 1000+ | 命中判定的抽签流由 seed 推出 |
| 墙钟 | 长局 `--wall-limit 10800 --episode-timeout 12600` | MD-AD-006 满局无争用已 ~5100 s |
| 每格 n | ≥3（含尾部模式的场景建议 ≥5） | 见 §4 尾部模式 |

## 4. 读数与判读规则

**(a) 只收当前评分口径的局**：`strategy_scorecard.scored_weight is not None`。
`scored_weight` 是**场景属性**（IE-01/02 = 0.9、IE-03 = 0.7、IE-04/05/06/07/MD-AD-006 = 1.0），
旧代码局没有该字段、分母不同，**不可与当前局合并求均值**。

**(b) 绝不跨 tag 平均**：每个 (场景, 种子, 臂族, tag) 一个格子。`rule` 在 IE-05 seed 7
有 8 局来自 p11..p18 八个 tag，直接平均得到 0.6663±0.2056 —— 那是**版本噪声**。
要用某 tag 必须显式指定（`_w1_paired_table.py --tag rule=p18`）。

**(c) 同种子配对**：`rule` / `rl` 在每个 (场景, 种子) 上基本是定值
（`rule` × MD-AD-006 seed 7 连续 8 局都恰好 0.4846），所以配对比较才是有效设计；
跨种子平均会把场景难度差（`rule` 在 IE-01 上 0.14–0.89）当成臂差异。

**(d) 尾部模式必须单独计数**：IE-01/IE-02 的时限是 900 tick。"打得死来袭者"会在
~60–160 tick 触发 `rule.intruders-destroyed` 提前收局；**打不死就拖满 899 tick**，
得分掉到 ~0.66。该模式**每条臂都有**（当前口径下 `rl` 3/15、`llm-rule` 2/6、
`llm-rl` v11 2/5），因此**不是任何 checkpoint 的退化**。
⇒ 这两个场景要报"分数分布 + 尾部占比"，不能只报"干净局均值"。

**(e) 显著性**：以同格重复的**格内 sd** 为标尺，`|Δ| < 2×合并 sd` 一律记为"不可判读"。
跨场景不能把 sd 混算。

**(f) 单架构与混合臂的成本差 15–20×**：LLM 臂 0.35–0.43 tick/s，
`rule`/`rl`/`rule-rl` 4–8 tick/s。所以 `rule` vs `rule-rl`（执行层主效应）
可以在 8 场景 × 5 种子上近乎免费地跑满，而含 LLM 的格子必须挑判别力最强的场景。

## 5. 已知混淆与限制（写进报告）

1. **规划带宽不可对齐**：规则执行器每 tick 重解，RL 执行层每 5 tick 决策。
   `llm-rule` 臂不能动 ⇒ 带宽差异无法从"执行器质量"里完全剥离。可用
   `--decision-interval 1` 做上界诊断（把 RL 带宽对齐到规则执行器）。
2. **IE-03 无判别力**：三配置各 n=3 的格内 sd ≥ 0.28、极差 ≥ 0.49、
   同场景同种子跨臂横跨 0.107→1.000。原因是 14 枚弹被 `overkill_cap=2`
   压成 6 发 × Pk 0.5 × 一中即毁 ⇒ P(≥3 命中) = 0.656，**约 1/3 的种子注定失守**。
   IE-03 只能用于链路/耗时检查。
3. **LLM 采样方差本身就是臂的方差**：`llm-rule` IE-05 seed 7 同配置重复 sd≈0.03，
   IE-03 可到 0.29 ⇒ 单次读数没有意义。
4. **目标来源约定**：见 §2；`llm-rl` 侧的等预算续训未完成前，规划层主效应是**打折的**。
5. **MD-AD-006 的结果近似二值**（守住 ≈0.52–0.59 / 失守 ≈0.11–0.47），
   sd 由模式比例而非精细质量决定 ⇒ 该场景要报**守住率**与分数均值两个数。
